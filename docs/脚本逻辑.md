## 一、当前形态

`yuketang-auto.user.js`（单文件，约 1200 行，`@run-at document-start`）

**功能**：视频页点「开始刷课」→ 2x 倍速 + 静音 + 防暂停 + 自动连播（播完自动跳下一个未完成视频）。
内嵌 always-on-focus，可后台挂机。状态面板 + 一键 BUG 上报。播放健康守护。

**覆盖域名**：`*://*.yuketang.cn/*`（华工 / 长江 / 其它部署一套代码）。

## 二、v2.0 为什么是重写而不是打补丁

2026 年雨课堂把课程播放页整体换掉了：

| 维度 | 旧版（v1.5 之前） | 新版（v2.0） |
|---|---|---|
| 视频页路由 | `/pro/lms/{sign}/{cid}/video/{leafId}` | `/ai-workspace/lms-graph/{cid}/video/{leafId}?node_id=…` |
| 课程页 | — | `/ai-workspace/lms-graph/{cid}`（另保留 `/pro/lms/{sign}/{cid}/unfinished`） |
| 完成度标记 | `span.text` 内容 `已完成` / `完成度：N%` | `.rate-detail .el-tooltip.text` |
| 目录（章节树） | 无统一结构，靠 `.btn-next` 反查 Vue `nextLeaf.id` | `.leaf-item` 列表：`.leaf-item-tag`（视频/讨论）+ `.leaf-item-title` + `.leaf-item-status`（进度饼/完成图标） |
| 「下一节」 | `.btn-next` + `__vue__` 拿到 `nextLeaf.id` | 顶部 `.control-right i.unit-arrow.arrow-reverse` |
| Vue 内部对象 | `el.__vue__` 可读 | **无**（生产构建 Vue 3，`__vue__` / `__vueParentComponent` / `__vnode` 全部 `undefined`） |
| 播放器 | `xt-*` Web Components + `<video>` | **同一个 `xt-*` 播放器**（这部分没变） |
| 进度上报 | 未知 | `POST /video-log/heartbeat/`，`videoend` 事件落地完成态 |

**关键结论**：旧的「DOM 爬成绩单 → Vue `nextLeaf.id` → 拼 URL」链路整条死掉。
但**播放器没换**，所以「原型链拦截 + 静音 + 倍速」这块可以原样保留——
这是 v2 能快速重写的基础。

## 四、几个必须记住的技术点

### 1. 进度上报靠 heartbeat，`videoend` 才落地「已完成」

```
POST /video-log/heartbeat/
{"heart_data":[{"i":5,"et":"heartbeat"|"videoend"|"loadstart",
                "cp":37.8,      // 当前播放位置
                "d":96.9,       // 视频总长
                "sp":1,"tp":0|3,
                "u":56002637,"c":2588039,"v":49200284,
                "skuid":13245176,"classroomid":26776303,"cc":"<校验串>",…}]}
```

- 播放中每约 5 秒一条 `heartbeat`，`cp` 按真实倍速推进（2x 时每 5 秒 +10 秒）
- 播到结尾发一条 `videoend`（`cp == d`）→ 服务端立刻把该视频标记完成
- 用 `GET /video-log/get_video_watch_progress/?video_id=…` 可读回 `{completed:1, watch_length, rate}`

**实测结论**：2 倍速播到结尾，服务端照样记 `completed: 1`（`watch_length` 甚至略大于 `video_length`），
说明它统计的是**视频时间轴**而不是墙钟时间 —— 倍速不会被判作弊。

### 2. 「下一个视频」用接口决定，不用 DOM

`todo_list` 接口的返回**天然带着课程顺序**，而且**播完的视频会立刻从清单里消失**：

```
开始            → count: {0: 64, 4: 9, 5: 1, total: 74}
刷完第 1 个视频 → count: {0: 63, …, total: 73}   且第一条变成「P16…」
```

`type` 字段：`0` = 视频，`4` = 讨论，`5` = 作业/考试。

于是 `pickNextVideo(list, currentLeafId)` 只要 `filter(i => i.type === 0)` 再取第一个，
就同时解决了两件事：
- **自动跳过讨论/作业**（不需要任何 DOM 判断）
- **自动判断「当前视频是否真的被服务端确认完成」**（`currentStillTodo`）——
  这是比读页面文案可靠得多的二次确认手段

### 3. 接口头部全部能从 `document.cookie` 拿到

第一版实测缺头部会直接返回 `{"msg":"XTBZ IS REQUIRED","error_code":40000}`。
需要的头部：

```
xtbz: cloud          ← document.cookie
university-id: 2627  ← document.cookie
platform-id: 3       ← document.cookie
x-client: web        ← 固定
terminal-type: web   ← 固定
x-csrftoken: …       ← document.cookie
```

全部可从 `document.cookie` 读取，**不需要碰 sessionStorage / 不需要额外的登录态注入**。

### 4. 必须显式赋值 `playbackRate` / `volume`

原型链拦截只在「有人给属性赋值」时生效。而播放器在页面初始化时（我们的钩子之前）
就已经设过一次 `playbackRate = 1` / `volume = 0.8`，所以**光装钩子不会变 2 倍速**。

`engagePlayback()` 必须显式 `video.playbackRate = 2`（会被钩子改写成目标值）、
`video.volume = 0`、`video.muted = true`，然后在 800ms / 2500ms 再补两次，
并由 1 秒守护持续纠偏 —— 实测 2 倍速可以稳定保持整段视频不减档。

（副作用：播放器自带的倍速 UI 仍显示 `1.00X`，因为它自己的状态变量没被更新。
但 `<video>.playbackRate` 真的是 2，功能不受影响。）

### 5. `location.href` 整页跳转 + localStorage 恢复会话

沿用 v1.5 的结论：跨 leaf 跳转用整页重载，避免前端组件状态泄漏。

- `goNext()` → `location.href = buildVideoUrl(ctx, leafId)`
- 引擎状态写在 `localStorage._ykt_engine_active`
- 新页面 `boot()` 检测到标记 → 自动 `startSession()`，用户无感

### 6. 纯函数导出给单测（避免镜像漂移）

v1.x 的做法是把纯函数「抄一份」到 `lib/core.js` 再对那份写测试，
结果覆盖率漂亮（97%）但**测的不是出货代码**，而且两边容易改一边忘一边。

v2 改成脚本自己导出：

```js
window._ykt.pure = { parsePageContext, parsePageType, buildVideoUrl,
                     pickNextVideo, buildApiHeaders, getVideoStatus,
                     formatDiagnosticsText };
```

测试直接 `import '../yuketang-auto.user.js'`（Vite 会执行这个 IIFE）然后测 `window._ykt.pure`。
代价是覆盖率数字变得难看（v8 覆盖 28% / 行 33%），但那是**真实数字**——
剩下 70% 是 DOM/播放器/接口代码，jsdom 本来就跑不了。

## 五、防御性设计（防死循环）

| 场景 | 护栏 |
|---|---|
| 服务端迟迟不确认完成 | 同一 leaf 最多重播 2 次，之后跳过继续下一个 |
| 连续找不到 `<video>` | 连续 3 次即停止并提示（防 404 / 空号死循环） |
| 播放卡死 | 停滞 45 秒才刷新，同一会话最多刷 3 次 |
| 播放异常结束（`gone`/`timeout`） | 同一 leaf 最多重试 2 次 |
| 接口全挂 | 退回点站内「下一节」箭头；再不行就停机报错，不瞎跳 |
| 主循环 | `while (guard++ < 500)` 硬上限 |

## 十、v2.1 倍速上限探查（2026-10）

### 起因

用户反馈：v1.x 试过多倍速，视频会「闪」，并被强制拉回 2 倍速。
既然现在有 Chrome DevTools MCP 能直接观测真实页面，就有条件把这件事查清楚。

### 结论一：「被强制拉回 2 倍速」的真凶是脚本自己

在关闭引擎（不装原型链拦截）的情况下把 `video.playbackRate` 设成 4，
164ms 后它自己变回 1。给 `playbackRate` 的 setter 挂日志，抓到调用栈：

```
设置 4  →  at pptr:evaluate（我的调用）
播放器改回 1 →  at v (fe/static/web/1.2.316/js/27437.*.js)
                <- HTMLVideoElement.dispatch
                <- h.handle (aiworkspace.*.js)
```

播放器**监听了 `ratechange` 事件**，在回调里把自己的内部倍速（默认 1）重新写回。
它并不做上限校验，只是「把值恢复成我以为的值」。

那为什么 2 倍速能用？因为脚本的原型链拦截会把这个 `= 1` 的赋值改写成 `= _yktRate`。
换句话说：**用户看到的「被拉回 2 倍速」就是脚本拦截把值改回了自己写死的 2**，
不是雨课堂的限制。「闪」则是另一回事（见结论二）。

### 结论二：真正的瓶颈是分片取流（实测数据）

视频源是 10 秒一段的 mp4（`...-10.mp4`）。逐个倍速实测 10~12 秒窗口：

| 目标倍速 | 实测有效速度 | waiting/stalled 次数 | 结论 |
|---|---|---|---|
| 2x | **1.99x** | 0 | 完美 |
| 3x | **3.00x** | 0 | 完美 |
| 4x | 1.63x | 22 | 明显卡顿，反而更慢 |
| 5x | 0.01x | 37 | 彻底崩掉 |

所以 2x 从来不是「限制」，3x 也能跑满；再往上播放器取不到流，越推越慢。

### 结论三：服务端不校验倍速

心跳报文里和倍速相关的字段：

- `sp`：**恒为 1**（多条视频、多种倍速下都一样）
- `rate`（进度接口返回的）：= `watch_length / video_length`，封顶 1，是完成比例而非倍速
- `tp`：观察上更像卡顿/暂停累计时长（4x 狂卡的那条视频 tp=22.3，干净的 2x 视频 tp=0）

没有任何字段把真实倍速传回服务端。混合 2x/3x 播完的视频照样 `completed: 1`。

### 方案：倍速阶梯 + 自适应降档

既然上限取决于取流而不是播放器，就不该写死一个值。v2.1 改为：

```js
const RATE_LADDER = [3, 2.5, 2];
```

`startHealthWatch()` 每 5 秒评估一次实测有效速度和窗口内卡顿次数，
满足 `shouldDropRate()` 就降一档，最低回到经过验证的 2x。
这样在能跑满 3x 的视频上白赚 50%，在跑不动的情况下自动退回安全值。

### 附带发现：进度上报存在可伪造的漏洞（未采用）

查 `watch_length` 判定逻辑时顺带做了几组注入实验。结论记录下来备查，
但**没有写进脚本**——它属于伪造数据，风险和 3x 播放不在一个量级。

**服务端靠什么判定完成**（`GET /video-log/get_video_watch_progress/`）：

```
{ last_point, watch_length, video_length, rate, completed, first_point, ult }
rate = min(1, watch_length / video_length)     completed 在 rate≈1 时置 1
```

- `last_point` 是客户端最后上报的 `cp`，服务端**只当参考**
- `watch_length` 是服务端**自己累计的已观看时长**，才是真正的判据

实验（全部在视频处于 paused、真实播放贡献为 0 的前提下进行）：

| 实验 | 结果 |
|---|---|
| 单发一条 `videoend`（`cp` 跳到 `d`） | HTTP 200，`last_point` 变成 `d`，但 `watch_length` 不动 → **`completed` 仍为 0** |
| 连发 `heartbeat`，`cp` 每步 +5 共 26 条 | `watch_length` 同步累计，最后 `completed: 1` → 154 秒视频**在暂停状态下 7.25 秒被判定完成**，且真的从未完成清单里消失 |
| 单条 `heartbeat` 直接 +75 | HTTP 200，但 `watch_length` 只计 **+25** → 单次计分有上限 |
| `cp` 已经到 `d` 后再连发 6 条 | 全部 200，`watch_length` **零增长** → 计分严格绑定在 `cp` 推进量上 |
| `cc` 字段复用旧值 | **HTTP 400** |

最后一条是关键约束：`cc` 是 32 位十六进制，前缀随视频固定、后缀随时间轮换
（同一个后缀 `FC9558351D509E7C` 在不同视频上都出现过）。
所以复用捕获到的旧报文会失效——真要做必须篡改播放器**自己正在发出的**请求，
借它的新鲜 `cc`。

**风险评估**：进度接口同时存了 `first_point` 与 `ult`（该视频会话的首末时间戳）。
本次注入实验里两者只差几秒，而视频长 154 秒——如果平台以后加一条
「`ult - first_point` 与 `video_length` 比值过高即告警」的规则，这种用法会被直接识别。

**结论**：漏洞存在且可稳定利用，但不纳入正式脚本。
